F9b. A refused conflict write is reported as a refused verdict write

One bounded case, one file. Each claim is measured by F9b-conflict-write.py in this folder, or labelled as read from the code. No verdict words of yours are used.

The case. One store command writes two records. The second is the annotation. If it is refused, the reply tells the host that the first, durable write did not happen.

The mechanism

cmd_verdict appends the verdict record, fsynced, then, when a different verdict already exists for that action id, appends a conflict record naming both sequence numbers and the rule. Both appends sit inside one try whose handler returns one reply for the whole command. So a refusal of the annotative write is reported as a refusal of the durable write before it, and the reply loses the action id it is about.

Injection

The benchmark ships a failpoint that refuses records of kind verdict before any bytes are written. I copied the benchmark, widened the selector in the copy to verdict or conflict, and ran four cells: control and injected, each through the wire so the reply is captured verbatim, and each with the real host process so the effect decision is the host's own. The copy is patched. The source is not.

Fifteen assertions, all met. Expected is the left column, observed is both.

Three findings, each bounded

1. The reply is false about durability. Two verdict records, each fsynced before the refusal, sit on disk when the reply says nothing is durable. Both frame digests recompute.

2. The event class collapses. A governance condition, two signed verdicts that disagree, reaches the host as a storage failure. The remedies differ: one sends an operator to a disk, the other sends a human to two decisions.

3. The annotation is lost, the finding is not. The rule text and the two sequence links are gone. The state is not, because replay recomputes conflicted from the two differing verdicts alone.

Your two corrections, applied

Governing effect was not contradicted. I wrote that earlier and withdraw it. The host emits the same three events with the same reason in both worlds. What is contradicted is the store's account of its own disk, not the host's conduct.

Indistinguishability has a scope. The two worlds are identical only to an observer holding the reply and the host journal. An observer holding the journal sees two verdict records. One holding the store's memory before the failure already reads conflicted.

That correction reaches further than the first. Because the state is recomputable, any reader with the journal distinguishes the worlds, so my stronger claim, that two worlds become identical and stay identical, does not hold. What survives is narrower: the reply states a falsehood about durability, and the reply is what the host must act on.

What the false statement invites

A client told its write did not land retries it. The same record sent again is refused in the same words and appends a third verdict, duplicate of the second, still with no conflict record. Measured. The control reply does not invite that, because it says stored: true.

Honesty note: retrying the control reply also appends, so this path is not idempotent in either world. Non-idempotence is a separate property and this case does not establish it. What it establishes is that the reply invites the retry while denying the write.

Limits

  • A failpoint, not a disk error. Same path, same exception, synthetic trigger. No real ENOSPC.
  • The annotation is refused before any bytes are written. A partial conflict write, and the repair

after a torn journal, are different cases and are not measured here.

  • One store, one action id, loopback, fixed keys, deterministic clock. No concurrency, no production

keys, no live traffic. Nothing here speaks to a deployed system.

  • The host is measured, not judged. It says nothing about a host that reads ok alone.
  • Read, not run: on a real write error the reply names no record kind. I did not force that path.
  • To close: a reply naming which write failed and what is already durable, and a check that a refused

annotation cannot change the class of the outcome.
