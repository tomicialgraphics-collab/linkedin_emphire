Your merge rate is measuring your reviewers.

GitHub says more than 40 percent of pull requests now start with an agent. That number has a denominator nobody publishes.

The report is out on 28 October. It was 17 percent in March, and about 110 million pull requests in September alone, six times the March volume.

Every one of those is a survivor.

A pull request exists because a person decided the draft was worth opening. The attempts that never got that far are not in the number, and they are the only place the interesting question lives. Is the agent getting better, or is the reviewer getting more willing to open whatever comes back?

The merge figures have the same shape. In February, 83 percent of agent-involved pull requests merged within two weeks, against about 86 percent for everything else. By September it was 90.

Read that as a trend and it looks like agents overtaking people. Read it as a measure of reviewers and it could be fatigue, a heavier mix of trivial changes, or both. The share is also a floor: GitHub counts only the agents it can detect.

A merge means somebody accepted a change. It does not mean the change was right, and it says nothing about how long the defect takes to surface.

What I would measure instead:

→ Attempts per merged pull request, on one team in one repo. If that ratio falls, the agent is improving. If the ratio holds while merge rate climbs, the reviewers are.

→ Time to detection for defects that reach main. The faster changes land, the wider that window, and the window does not appear in a defect count.

→ Review time per pull request, because that is where the cost moved. Writing got cheaper. Checking did not.

The part nobody tells you:

If the headline metric is a human decision, then the headline metric measures the human. That is fine as long as you know it, and expensive the moment you quote it to a board as evidence of quality.

What does your team count: the pull requests that landed, or the attempts it took to get one that did?
