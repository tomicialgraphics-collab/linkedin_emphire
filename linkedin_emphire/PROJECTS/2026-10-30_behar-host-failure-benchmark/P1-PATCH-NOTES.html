P1: the four recovery and authority items

Olusanya Timothy. 1 November 2026.

This is the second patch in the exchange. The first (P0) made the verifier reject the counterexamples the review supplied. This one fixes the four items the review listed as P1, and it is a single commit on top of the P0 branch.

Base: 9194c61 (p0-authenticated-recovery), which is 3b6b781 on 25cd57f. The patch applies clean to a fresh checkout of 9194c61 and, as the cumulative variant, to 25cd57f directly. Applied and tested on main at df0cf5a, which is the commit these notes describe.

The four, one at a time

F11 the store indexed a record in memory before appending it to its journal, so for the length of one write it reported a decision a restart would not have the journal append happens first and the sequence number is only consumed once the bytes are on disk; a journal that refuses a write returns ok: false, durable: false and memory is untouched journal-first
F7 a repair truncated a torn journal and reported how many bytes it dropped, then dropped them the discarded tail is copied to store.jsonl.quarantine-N.bin before the truncation, and the repair record carries that file's name, byte count and sha256 repair-quarantine
F9 (state half) two verdicts for one action resolved to whichever record a component read first a second verdict that differs from the first is recorded as a conflict naming both sequence numbers, the state becomes conflicted, and neither record closes the gap. The verifier recomputes the same rule from the journal conflict
F10 the host logged an effect whether or not the store's reply answered the request it had made a reply counts only if it is well formed, reports success, and names the action that was asked about. Anything else produces reply_rejected with the reasons, and the effect is withheld reply-checked

Two of these are orderings inside a process and two are defects in what the artifacts contain. That distinction is carried into the regression suite: F7 and F9 are counterexamples that damage the evidence, F10 and F11 are counterexamples that restore the old code. Mutating an artifact cannot demonstrate a bug that lives in the order of two writes, and a suite that pretended otherwise would be testing its own mutation.

Three probes

None of these four can be shown inside the main run without damaging the record the rest of the suite depends on. So run.py runs three short probes at the end, each in its own directory, each with its own journal where it needs one:

  • probe-durability starts a store with HFB_FAILPOINT=verdict, which makes the journal refuse a verdict write before any bytes are produced. It asks for a verdict, then asks the same process what it knows, then restarts the store and asks again. The expected answers are: ok: false, nothing, nothing.
  • probe-repair writes a two-record journal with a third record cut mid-line, starts the store on it, and lets the repair happen. The verifier then requires the repair record's quarantine file to exist with the byte count and digest the repair claims.
  • probe-reply starts bench/stub_store.py, a fixture that answers every request, succeeds at every request, and names S-0000 in every verdict reply. Host scenario E ships a verdict to it. The expected answer is a named rejection and no effect.

The failpoint is a test hook inside the store, not a simulated disk failure. It refuses the write at the one moment the ordering matters, which is what makes the result checkable; it does not stand in for a full disk, a dying device, or an interrupted fsync. That limit is the same one the note states about the whole suite.

Three things that will look like regressions

example/run is regenerated again, because the artifact set changed: the three probe directories are now part of a run, and the manifest lists them. The old example fails the new completeness check, which is the correct outcome.

The check count moves from 16 to 20.

Two fields in the store journal changed name and meaning. replayed_seq was journal.seq - 1, which was wrong by one and read as though it were a sequence number. It is now replayed_records, and it is the count of records the replay recovered: 2 for a two-record journal, 0 for a fresh one. Any reader that was parsing the old field should read the new one, and the repair record now also carries the quarantine fields.

What is still open

Identifiers are still chosen by the caller. The store records the registration and, since the P0 patch, the note says "registered" rather than "issued". Making the store mint the id is a five-line change to the protocol and a large change to the scenarios: A' exists to show silence when no prior expectation was registered, and under strict minting any action the host can name is one the store already knows about. That row would have to be recast, and recasting it changes the scenario table rather than fixing a defect. I would rather put that to you as a design question than ship it inside a bug-fix patch.

Also unchanged: an idle connection can still hold the store (F15); the verifier still imports the encoder it checks, so the correlated-oracle problem stays until there is a second encoder; and there is no CI matrix, so the cross-platform claim is still two runs compared by hand.

Applying it

On top of the P0 branch:

git checkout p0-authenticated-recovery
git apply host-failure-benchmark-p1.patch
git add -A
git commit -m "P1: journal before memory, repair that keeps its bytes, named conflicts, checked replies"
git push -u origin p0-authenticated-recovery

git add -A && git commit -m "P0 and P1"

Two defects found on Windows, and the platform note corrected

The first Windows run of P1 found two defects in verify.py, both by mistaking the shape of a path, and both are the verifier contradicting something this document claims about it.

The first: verify.py pointed at a directory that does not exist printed a failed check and then raised FileNotFoundError while trying to write its own report. The P0 notes say the verifier never raises. It raised.

The second is the worse one. verify.py run-a run-b, given two directories that are both absent, reported determinism holds. Absent compared to absent is a match in the only sense a byte comparison can see, and that sense is none. Two absent runs were being called identical, which is the same defect as a missing artifact passing a completeness check, in the tool that exists to catch exactly that.

Both are fixed in a third commit, and both are now tests rather than fixes: challenge.py gained two input checks, so a path that is not a run has to be refused with exit 2 and no traceback, and a comparison has to fail when either directory is missing an artifact. The comparison also requires both directories to exist and every artifact to be present in both before it compares a byte.

Neither defect affects any result in this document. Every number below was produced by a run that existed, and the eight counterexamples in P0 and the four in P1 were caught by checks that never went through either path.
