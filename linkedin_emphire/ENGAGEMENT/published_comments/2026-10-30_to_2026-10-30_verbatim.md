The line isn't in the grammar. It is in what survives after the call
ends. An IVR menu is enumerated: every path and every dead end exists
before the call starts, and its failures are finite and known. A voice
agent decides mid-call, and its failure space is open.

So I draw the line at the postmortem. When the caller says you moved
it to the wrong day, can the system reconstruct from the record what
was actually heard, what was decided, which tool call fired, and why?
Your own interruption layer says the context should only hold the
words the caller actually heard. That is the record, not a UX
preference. And the grading layer only holds if the judge's answer
can be re-derived from the stored recording and transcript, not just
written to a dashboard.

An IVR with better grammar fails in known ways. A voice agent that
cannot replay its own call fails in ways nobody predicted, and cannot
say which.

## DIRECT OWNER QUESTION (not a post capture) 10-30: "Why must a
reported number always be accompanied by an environment fingerprint?"

### INPUT
Owner asked, in chat: "Why must a reported number always be
accompanied by an environment fingerprint"

### THOUGHT (the reasoning, as answered in chat)
- Core reframe: a reported number is NOT a fact about the system.
  It is a measurement of one specific (system, environment) pair at
  one specific moment. The number alone carries no system, model
  version, prompt, library, data, seed, hardware, or time. Without
  the fingerprint the number is an orphan, attached to nothing
  pointable.
- Mechanic 1 (relational): the number is a function of code
  revision, model+version, prompt, dependencies, data, seed,
  hardware. Change any one input and it moves. Analogy: a
  temperature reading with no location or time tells you the
  thermometer worked, not what was measured.
- Mechanic 2 (re-run != re-derive): the one that bites. A re-run
  next month yields a number from next month's environment, not the
  original. Only the recorded environment keeps the original number
  tied to its own run. No fingerprint and the number floats free of
  its producer; every re-run silently replaces it with a different
  number that looks identical.
- Mechanic 3 (independent re-derivation): an auditor/insurer/
  diligence team re-derives a number only if they have the
  environment. Without it, "verification" is the team testifying
  how it ran, i.e. a debrief, not a verification.
- Mechanic 4 (comparability): 0.94 vs 0.91 is a comparison only if
  the two environments are known; otherwise the delta is a coin flip
  about whether the environments even match.
- Mechanic 5 (failure isolation): when a number drops, the
  fingerprint distinguishes a model bump from data drift from a
  library change; without it, debugging is guesswork and "system
  got worse" is indistinguishable from "environment moved."

Build me an app” is not the same as “run it, connect it to a service, publish it, and schedule it.” Those are different actions, with different consequences.

The useful question isn't only what the agent was asked to do. It’s what it can do without another person’s approval.

I’d check the permissions in stages:

Can it read files beyond the project it is working on?

Can it execute code, install packages, or change the environment?

Can it reach a network or send data to an external service?

Can it create something that persists after the session, like a scheduled task?

Can it publish, deploy, or affect someone else?

Writing code in a disposable workspace is a different risk from running that code on your machine. Suggesting an API is different from sending data to it. Preparing a deployment is different from making it public. Keep those actions separate, and make the boundary visible before the agent reaches it.

This doesn't mean asking for approval after every small step. That trains people to click through. Let the agent move quickly inside a safe workspace. Require a person to decide when it crosses into another system, exposes data, or creates a lasting change.

The prompt describes the task. The permission set defines the possible side effects. If the two are treated as the same thing, a helpful agent can do much more than anyone intended.

Autonomy should save us from micromanaging the work, not from deciding what the system is allowed to do.

Where would you draw the boundary?
